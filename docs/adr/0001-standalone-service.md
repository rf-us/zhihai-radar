# ADR 0001：作为独立服务存在，而不是 RFERP 的一个模块

- 状态：已接受
- 日期：2026-11-26

## 背景

知海选品雷达需要把"选品结论"落到 ERP 的产品与 BOM 上。最初方案（v1）是在 RFERP 仓库内
新增一个业务域：加迁移、加权限模块、加导航、加接口。

## 决策

改为**独立仓库 + 独立服务**，只通过 RFERP 的公开 HTTP API 对接。

## 理由

1. **许可证**。RFERP 仓库没有 `LICENSE` 文件，默认保留所有权利。阅读、复制、修改其源码
   在法律上都含糊；仅通过公开 API 调用则是正常使用。
2. **合规举证**。比赛要求"核心功能与主要创新由团队独立形成"。一个只包含自己代码的公开
   仓库，是这个命题最直接的证据。
3. **演进解耦**。v1 需要跟随 RFERP 的迁移版本号、权限矩阵、导航契约测试与 Go 接口变化。
   独立服务只需要守住一份窄接口（11 条端点）。
4. **可替换性**。接口层抽象之后，换成别的 ERP 只需要重写 `internal/reef`，选品能力不受影响。

## 代价

- 跨服务没有事务，采纳必须写成 Saga 并处理"不确定态"；
- 两个进程，演示需要一键脚本；
- 用户要在 radar 里登录一次（radar 代登录 RFERP，token 只存服务端内存）。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| fork RFERP 后改造 | 许可证含糊；合规叙事被动；跟随上游演进成本高 |
| 共享数据库 | 跨进程耦合 schema，RFERP 升级即失效 |
| CSV 导入导出 | RFERP 没有产品导入功能，只有整库恢复，不可用 |
| 把 radar 做成 RFERP 的插件 | RFERP 没有插件机制，实现它等于改源码 |
